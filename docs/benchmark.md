# Benchmark procedure

Run the app locally, then opt in:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/benchmark-local.ps1
```

This creates a dedicated synthetic student/category via the API, then bulk-inserts **10,000** tickets and creation events in one database transaction. Every benchmark student has exactly that dataset. Tickets are OPEN with mixed HIGH/MEDIUM priority and synthetic timestamps spaced one second apart. Repeated runs create new students/datasets and increase the whole database; compare before/after **within one run**, not across runs.

Query evaluated:

```sql
SELECT id, title, status, created_at
FROM tickets
WHERE creator_id = :student_id
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

The selected index is `tickets_creator_created_idx(creator_id, created_at DESC, id DESC)`. The creator equality narrows to visible rows and the remaining columns match the requested order. It avoids sorting all of that student's tickets. This does not establish that every combination of filter/title search/sort has the same performance.

`DatabaseBenchmark.java` captures `EXPLAIN (ANALYZE, BUFFERS)` and measures a baseline without that index. The drop occurs **inside a transaction that rolls back**, restoring the index even on failure. It then captures the indexed plan and runs the same samples with the index. Rows, query, connection, warm-up and machine stay constant. Each database workload has 100 warm-ups, 500 measured requests, concurrency 1. Metrics include JDBC/network/result consumption, exclude application authentication/JPA/JSON, and are labeled database via JDBC. These short loops are comparative smoke benchmarks, not production capacity tests. Warm cache and JVM/database effects limit interpretation; the baseline always runs first.

The API benchmark independently calls the actual student ticket-listing endpoint with default createdAt descending order/size 20. It checks that the student sees exactly 10,000 rows and 20 results per page. It uses 20 warm-ups, 100 measured requests, concurrency 4. API time includes token validation/account lookup, visibility predicates, count query, entity fetching and JSON. There is no API before/after comparison and no claimed API speedup.

Output under ignored `.local/benchmark/`:

- `before-plan.txt`, `after-plan.txt`: real execution plans.
- `before.json`, `after.json`: database metrics (median, nearest-rank p95, throughput, measured duration, error rate).
- `api.json`: separate HTTP metrics, OS and logical CPU count.

The seed requires database-owner access in the local development configuration. Do not run it against production or a shared database. The temporary index drop can block other requests, so keep this a quiet local experiment. Sample arrays are held in memory; tickets are generated by SQL, not loaded into Java. On an error the procedure fails or records the API error rate; it never invents missing results.

## Results

Measured on 14 October 2026, Windows 11 (build 26200), AMD Ryzen 5 6600H, 6 cores/12 logical CPUs, approximately 15.3 GiB OS-reported RAM, Java 21.0.12.1 and PostgreSQL 17.6. The application and database ran on the same machine. The table contained 10,001 tickets: the walkthrough's closed ticket plus the benchmark student's 10,000 OPEN tickets. No load generator other than this procedure was used.

| Workload | Warm-up / samples | Concurrency | Measured duration | Median | p95 | Error rate | Throughput |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Database via JDBC, creator index removed temporarily | 100 / 500 | 1 | 4.223 s | 8.244 ms | 12.497 ms | 0% | 118.402 requests/s |
| Database via JDBC, creator index restored | 100 / 500 | 1 | 0.202 s | 0.366 ms | 0.503 ms | 0% | 2472.599 requests/s |
| Application HTTP API, index present | 20 / 100 | 4 | 1.469 s | 51.905 ms | 88.792 ms | 0% | 68.068 successful requests/s |

Captured baseline plan: sequential scan of 10,001 rows, filter to 10,000, then top-N heapsort; 182 shared buffer hits, execution 13.680 ms. Indexed plan: `Index Scan using tickets_creator_created_idx`, returning 20 rows; 3 shared buffer hits, execution 0.051 ms. EXPLAIN instrumentation and one-shot timing are different from the repeated JDBC samples above.

Committed evidence: [baseline plan](benchmark-results/before-plan.txt), [indexed plan](benchmark-results/after-plan.txt), [baseline metrics](benchmark-results/before.json), [indexed metrics](benchmark-results/after.json), [HTTP metrics](benchmark-results/api.json).

These are **short local smoke measurements**, especially the 0.202-second indexed loop. They show the chosen query/index behavior, not a production throughput capacity or SLA. The API includes a count query and full response mapping that the database-only query does not; do not compare their throughput as if they were identical work. No API before/after speedup, availability or real user count is claimed.
